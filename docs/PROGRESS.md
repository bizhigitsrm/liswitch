# Журнал разработки расширения liswitch (liswitch@local)

Проект: расширение для GNOME Shell 51 (GJS 1.90, только Wayland), улучшающее переключение раскладок клавиатуры.
Файл `docs/PROGRESS.md` является единственной долгосрочной памятью проекта между этапами разработки.

---

## Этап 1. Исследование и справка по API

- **Дата выполнения**: 2026-11-14
- **Статус**: Выполнен

### Что сделано
1. Исследован рантайм GNOME Shell 51.1, Mutter 51.1 и GJS 1.90.1 (Fedora 45 Workstation).
2. Выгружены и детально изучены 200 исходных файлов JS подсистемы GNOME Shell 51 из встроенного ресурса `libshell-51.so`.
3. Разобрана архитектура управления раскладками в `resource:///org/gnome/shell/ui/status/keyboard.js`:
   - Механизм `getInputSourceManager()`, устройство `InputSourceManager` и `InputSource`.
   - Сигналы `current-source-changed`, `sources-changed`, `keymap-changed`.
   - Различие между интерактивной сменой раскладки (`activate(true)` с обновлением MRU) и тихой сменой (`activate(false)` для восстановления состояния окон).
4. Проанализированы системные схемы GSettings:
   - `org.gnome.desktop.input-sources`: ключи `sources`, `current` (подтверждено, что устарел и игнорируется), `mru-sources`, `xkb-options`, `per-window`.
   - `org.gnome.desktop.wm.keybindings`: ключи `switch-input-source` и `switch-input-source-backward`.
5. Изучены механизмы регистрации горячих клавиш: `Main.wm.addKeybinding`, `Main.wm.removeKeybinding`, флаги `Meta.KeyBindingFlags` и режимы `Shell.ActionMode`.
6. Изучено отслеживание фокуса и окон в Wayland: сигнал `notify::focus-window` на `global.display`, свойства и методы `Meta.Window` (`get_id()`, `get_wm_class()`, `get_sandboxed_app_id()`), сигнал очистки окна `unmanaged`.
7. Изучено создание индикатора панели на базе `PanelMenu.Button`, `Main.panel.addToStatusArea`, виджетов `St.Label` и структуры `PopupMenu`.
8. Изучено тестовое окружение GNOME 51: запуск сессии без `--display-server` (вложенный режим по умолчанию), опция `--devkit`, запуск тестов расширения через `gnome-shell-test-tool --extension`, команды утилиты `gnome-extensions`.
9. Сформирован детальный справочник в файле `docs/api-notes.md`.

### Принятые решения и обоснования
1. **Строго синхронный `disable()`**: подтверждено по исходникам `ui/extensionSystem.js`, что возврат `Promise` в GNOME 51 вызывает исключение `disable() must not be async`. Все операции отключения должны выполняться синхронно.
2. **Уникальная роль индикатора в панели**: в `Main.panel.addToStatusArea` запрещено повторно использовать роль `'keyboard'` (вызывает конфликт расширений). Расширение будет регистрировать роль `'liswitch'` и, при необходимости замены, скрывать системный индикатор через `Main.panel.statusArea['keyboard']?.hide()`.
3. **Игнорирование ключа GSettings `current`**: переключение раскладок будет производиться строго через `InputSource.activate()` или `InputSourceManager.activateInputSource()`, так как запись в `current` задепрекейчена и не обрабатывается Shell.
4. **Обязательное подключение к сигналу `unmanaged`**: для предотвращения утечек памяти при отслеживании окон в Wayland все внутренние кэши окон должны очищаться по сигналу `unmanaged`.
5. **Учёт доступности движения (`St.ReducedMotion`)**: любые анимации индикаторов и переходов обязаны проверять `St.Settings.get().reduced_motion !== St.ReducedMotion.REDUCE`.

### Оставшиеся VERIFY и риски
1. `// VERIFY:` Влияние глобального фильтра событий Clutter Stage (`global.stage.connect('captured-event', ...)`) на задержку ввода — если на последующих этапах понадобится перехват клавиш до того, как они попадут в Wayland-клиент.
2. Риск конфликта с пользовательскими комбинациями в `org.gnome.desktop.input-sources xkb-options` (например, Alt+Shift, перехватываемый на уровне libxkbcommon через `modifiers-accelerator-activated`).

### Созданные и изменённые файлы
- `docs/api-notes.md` — справочник по API GNOME Shell 51, подводные камни, ограничения Wayland, открытые вопросы.
- `docs/PROGRESS.md` — журнал проекта и фиксация результатов Этапа 1.

## Этап 2. Спецификация и архитектура

- **Дата выполнения**: 2026-11-14
- **Статус**: Выполнен

### Что сделано
1. Разработана функциональная спецификация проекта `docs/spec.md` для MVP:
   - Каждая функция (F1: Индикатор панели, F2: Горячие клавиши и управление конфликтами, F3: Запоминание раскладки по приложению/окну, F4: Всплывающий OSD, F5: Окно настроек Libadwaita, F6: Концепция этапа 9) описана по строгому шаблону «поведение → граничные случаи → как проверить».
   - Детально описана стратегия разрешения конфликтов с системным `switch-input-source` GNOME Shell и ограничения аппаратных модификаторов `xkb-options`.
   - Составлена сводная матрица ручного приёмочного тестирования (T-F1.1 — T-F5.2).
2. Разработан комплексный архитектурный документ `docs/architecture.md`:
   - Сформировано модульное дерево проекта на базе стандартных ES-модулей (папка `src/`).
   - Разработана полная схема GSettings `org.gnome.shell.extensions.liswitch.gschema.xml` (все ключи с типами, умолчаниями и локализуемыми описаниями).
   - Построены диаграммы жизненного цикла: последовательность инициализации в `enable()` и строго синхронного демонтажа в `disable()`.
   - Определены границы модулей (`InputSourceService`, `WindowMemoryService`, `HotkeyManager`, `IndicatorService`, `OsdService`), их публичные методы и события.
   - Составлена детальная матрица владения ресурсами («Ресурс → кто создаёт → кто уничтожает»).
   - Описаны сценарии обработки нештатных ситуаций (недоступность `InputSourceManager`, пустой список раскладок, динамическое удаление раскладок).
   - Сформулирована и обоснована политика поведения на экране блокировки (`session-modes: ["user"]` без `unlock-dialog`).
   - Зафиксированы правила безопасности и приватности (гарантированное отсутствие кейлоггинга, внешних процессов и телеметрии).

### Принятые решения и обоснования
1. **Исключение `unlock-dialog` из `session-modes`**: в `metadata.json` указывается только `["user"]`. Расширение автоматически выгружается на экране блокировки, гарантируя стабильность PAM-диалога ввода пароля и соблюдая гайдлайны безопасности EGO.
2. **Модульная структура в `src/`**: разделение ответственности между специализированными сервисами исключает разрастание монолитного кода в `extension.js` и упрощает изолированное тестирование.
3. **Синхронный LIFO-демонтаж**: все ресурсы уничтожаются строго в обратном порядке создания (`Indicator` → `Hotkeys` → `OSD` → `Memory` → `InputSources` → `Settings`). Возврат промисов исключён.
4. **Тихая активация (`interactive = false`) для памяти окон**: при смене фокуса активная раскладка восстанавливается через `activate(false)`, что обновляет состояние Mutter/XKB без перетасовки системного списка `mru-sources`.
5. **Безопасное замещение системных шорткатов**: перехват системного `<Super>space` выполняется только при явном согласии пользователя с обязательным сохранением исходных значений в `backup-system-switch-keys` и 100% восстановлением в `disable()`.

### Оставшиеся VERIFY и риски
1. `// VERIFY:` Синтетическая эмуляция шорткатов выделения/вставки (`Shift+Ctrl+Left`, `Ctrl+X`, `Ctrl+V`) через виртуальное устройство ввода Mutter для перспективной функции F6 (Этап 9).
2. Проверка поведения при одновременной активности системной опции `org.gnome.desktop.input-sources per-window` (рекомендуется автоматически отключать системный флаг на время работы расширения).

## Этап 3. Каркас проекта и среда разработки

- **Дата выполнения**: 2026-11-14
- **Статус**: Выполнен

### Что сделано
1. Создан манифест расширения `metadata.json` с поддержкой GNOME Shell 51, UUID `liswitch@local`, схемой GSettings `org.gnome.shell.extensions.liswitch`, gettext-доменом `liswitch` и режимом сессии `["user"]`.
2. Создан базовый модуль расширения `extension.js` с классом `LiswitchExtension extends Extension`:
   - Строго синхронные методы `enable()` и `disable()`.
   - Инициализация `this._settings = this.getSettings()` в `enable()` и гарантированное обнуление ссылки `this._settings = null` в `disable()`.
   - Логирование факта включения/отключения с версией из метаданных.
   - Полный отказ от устаревшего `imports.*`, строгие стандартные ES-модули.
3. Создана минимальная схема GSettings `schemas/org.gnome.shell.extensions.liswitch.gschema.xml` с путем `/org/gnome/shell/extensions/liswitch/` и ключом `debug` (boolean, default: false).
4. Создан модуль параметров `prefs.js` с классом `LiswitchPreferences extends ExtensionPreferences` на базе Libadwaita (`Adw.PreferencesPage`, `Adw.PreferencesGroup`, `Adw.SwitchRow`) с двухсторонней привязкой флага `debug` через `Gio.SettingsBindFlags.DEFAULT`.
5. Создан файл стилей `stylesheet.css`.
6. Разработан `Makefile` с целями `schemas`, `pack`, `install`, `uninstall`, `enable`, `disable`, `logs`, `nested`, `lint`, `clean`.
7. Сконфигурировано окружение разработки:
   - Конфигурации ESLint: современный плоский конфиг `eslint.config.js` и совместимый `.eslintrc.json`, настроенные под GJS/GNOME Shell (глобалы `global`, `globalThis`, `_`, `C_`, `N_`, `log`, ES2022, без глобалов Node.js/браузера).
   - `.editorconfig` (стандарты отступов 4 пробела для JS, 2 для JSON/XML, табы для Makefile).
   - `.gitignore` (исключение архивов `.zip`, `.shell-extension.zip`, скомпилированных схем, временных файлов).
   - `README.md` с кратким описанием и инструкциями по сборке/запуску.
   - `LICENSE` с текстом GPL-2.0-or-later.
8. Разработан скрипт `scripts/dev-run.sh` для быстрого цикла разработки: сборка схем, проверка линтером, упаковка, установка и проверка расширения.
9. Проверена валидация схемы через `glib-compile-schemas --strict --dry-run schemas/` и работа `make lint`, `make pack`. Проверена целостность и состав формируемого пакета расширения.
10. Разработан автоматизированный тест `tests/smoke-test.js` для `gnome-shell-test-tool --headless` с проверкой регистрации расширения и 10 циклов `disable`/`enable`. В `Makefile` добавлена цель `test`.

### Принятые решения и обоснования
1. **Поддержка двух форматов ESLint (`eslint.config.js` и `.eslintrc.json`)**: плоский конфиг является стандартным для ESLint 9+, а `.eslintrc.json` гарантирует совместимость со старыми версиями инструментария и внешними IDE.
2. **Включение `stylesheet.css` и `LICENSE` в архив пакета**: передача через флаги `--extra-source` в `gnome-extensions pack` обеспечивает соответствие правилам дистрибуции extensions.gnome.org (наличие файла лицензии и таблицы стилей).
3. **Двусторонняя привязка через GSettings в `prefs.js`**: использование `settings.bind()` для `Adw.SwitchRow` гарантирует автоматическую синхронизацию UI настроек без ручных слушателей сигналов.
4. **Фолбэк проверки синтаксиса в `make lint`**: при отсутствии глобального бинарника `eslint` линтер автоматически запускает строгую проверку синтаксиса ES-модулей через `node --check`, гарантируя обнаружение синтаксических ошибок на этапе сборки.
5. **Лицензия GPL-2.0-or-later**: выбрана стандартная лицензия экосистемы GNOME Shell, совместимая с правилами публикации на extensions.gnome.org.
6. **Отказ от `dbus-run-session gnome-shell --wayland --no-x11` для вложенного тестирования**: подтверждено практическим запуском в GNOME 51, что Mutter не имеет вложенного Wayland-клиента и завершается ошибкой `EBUSY` при попытке захвата DRM-устройств через `systemd-logind`. Изолированное тестирование расширения переведено на официальный headless-раннер `gnome-shell-test-tool`.
7. **Инструкции по первичному обнаружению расширения в Wayland**: задокументировано, что GNOME Shell сканирует `~/.local/share/gnome-shell/extensions` только при старте. При первой установке из CLI требуется перезаход в сессию (relogin) или однократная загрузка через Looking Glass (`Main.extensionManager.loadExtension(...)`).

### Оставшиеся VERIFY и риски
1. `// VERIFY:` Интерактивное тестирование нового композитора в GNOME 51 возможно только на отдельном виртуальном терминале (TTY3), так как запуск второго экземпляра GNOME Shell на том же месте блокируется logind (конфликт DRM-устройств).
